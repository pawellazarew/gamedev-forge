## 1. Запрос и вердикт

Запрос Павла: «В платформу надо добавить не только движок, но и тестирование игр с аналитикой, оценкой качества картинки и процесса, чтобы явно видеть, как агент гоняет и какие цифры показывают прогоны».

Вердикт одной фразой: новый продукт не нужен — нужна **память**. `game-forge` хорошо меряет один прогон и не помнит ничего. Добавляем запись о каждом прогоне (кто, что, на какой сборке, с какими цифрами), сравнение двух записей и три честных слоя цифр поверх: игра, картинка, процесс. Живое наблюдение за агентом — работа Пульта, не Forge.

## 2. Как принималось решение

10 агентов: 5 инвентаризаций (код `game-forge`, оба существующих design doc'а, визуальные критики, Пульт и транскрипты, веб-ресёрч по SOTA качества картинки), 2 архитектуры-кандидата (продуманы на Opus), 3 независимых критика. Один инвентаризационный агент вернул заглушку вместо результата — инвентаризацию Пульта пришлось перезапускать отдельно, и в перезапущенном прогоне она вошла в инвентаризации кода/планов/визуальных активов.

Два кандидата:
- **lean-ledger** (1,5 дня) — один маленький файл на прогон + `forge compare` + дешёвые детерминированные метрики картинки первыми; VLM-мнение — аннотация, никогда оценка и никогда гейт.
- **full-observatory** (17 дней) — то же самое плюс `forge watch` (живой просмотр прогона), калиброванный `lookElo` (Elo-рейтинг картинок по парным сравнениям VLM), `forge bench` (кросс-игровая доска метрик).

| Критик | lean-ledger | full-observatory | Ключевой вывод |
|---|---|---|---|
| Продюсер | 8 | 4 | full-observatory = весь бюджет Г1+Г2 без запаса; `forge watch` и `lookElo` — самые дорогие и наименее нужные пункты |
| Скептик достоверности | 7,5 | 5,5 | `lookElo` переоценивает точность: на 10 парах согласие имеет разброс ±25 п.п., «калиброванный» — не то слово; `forge bench` агрегирует несравнимые между играми числа |
| Codex | без числа — рекомендует направление lean-ledger, отклоняет обе оценки трудозатрат | — | 2 блокера + 6 крупных проблем на обоих дизайнах разом, разбор в §13 |

Все трое сошлись на **lean-ledger** как правильном размере, но каждый предложил своё сужение. Этот документ — гибрид с внесёнными фиксами Codex, а не сырой lean-ledger: где источники расходятся, в силе то, что написано здесь — в частности, один JSON-файл на прогон вместо общего `ledger.jsonl` (снимает блокер Codex про конфликты слияния в PR-флоу «ветка на шаг»), идентичность автора прогона через `CLAUDE_CODE_SESSION_ID` вместо экспортируемых агентом переменных, «неубедительно» вместо «шум» для статистики, `forge watch`/`lookElo`/`forge bench` не строятся вовсе, golden сначала только логируется.

## 3. Что уже есть и чего нет нигде

**Уже есть** (по коду, не по памяти):
- `forge probe`: `frameWorkMs`/`frameWorkP99Ms`, `headroom`, `mainThreadBusy`, `drawCallsMedian`/`P99`/`Max`, `longFrameRatio`, `heapMb`, `bundleKb`, `loadMs`, `errorCount`, `pixelChange`, вердикт `frame-alive`. Вердикт pass/warn/fail по бюджетам из `forge.config.mjs`.
- `forge sim` + `analyze`: `winrate` с интервалом Уилсона (**интервал Уилсона** — доверительный интервал для доли, точнее обычной формулы при малом числе прогонов; поля `winrateLo`/`winrateHi`), `medianSeconds`/`p10Seconds`/`p90Seconds`, `clearRate` по уровням, флаги `wall`/`spike`/`flat-curve`/`boring`/`skill-flat`/`skill-cliff`/`bot-suspect`/`timeout`.
- `forge shots`/`play`: сценарии, `expect()`-проверки, PNG. `forge report`: одна статичная HTML на один прогон. `forge critique`: бриф для критика, не оценка.
- Цифры картинки существуют, но нигде не сохраняются: echo-art-critic считает clip%, перцентили яркости, попадание в палитру, долю тёмных пикселей inline-скриптом — результат живёт только в ответе чата. `game-asset-generator`: взвешенная рубрика по 5 критериям на один ассет, без свода.
- Практики: 100%-кропы, два варианта, независимые ревью Codex и Claude, выбор за Павлом.

**Чего нет нигде** (и в планах тоже):
1. Истории прогонов: каждый запуск пишет новую папку `.forge/<kind>-<stamp>/`, старые никто не читает (у bum2billionaire — 20 `probe-*`, 77 `play-*`, 29 `sim-*`); всё, кроме `JOURNAL.md`, в `.gitignore`; сравнения двух прогонов нет.
2. Записи «кто запускал»: ни сессии, ни агента, ни ревизии кода в `probe.json` нет.
3. Цифр картинки, сравнимых между прогонами.
4. Метрик процесса — а kill-критерий Г1 («число итераций агента до фикса не упало») без них не измерить.
5. Живого вида идущего прогона.

Уже запланировано и остаётся неизменным: телеметрия ботов и тестеров (`ForgeEvent`, `forge collect`), `pixel-diff`, тюнер, `replay`, `invariants`, `golden`, `budget`, манифест прогона (назван в §10 движка, но не специфицирован — этим документом специфицируется).

## 4. Запись о прогоне (run record)

Основа всего дизайна. Один маленький JSON-файл на прогон вместо общего append-файла: `<game>/.forge/ledger/<YYYY-MM-DD>/<run_id>.json`, **коммитится**. Отдельный файл вместо одной строки в общем `ledger.jsonl` — решение блокера Codex: общий файл конфликтовал бы при squash-мёрже параллельных PR; новые файлы с уникальными именами не конфликтуют никогда.

- `run_id = <game>-<UTC ts>-<h6>`, где `h6` — первые 6 hex от sha256 канонического манифеста.
- Манифест пишется **до** запуска и не меняется. Результат дописывается **после** запуска, в том же файле, одной атомарной записью.

| Блок | Поле | Когда пишется |
|---|---|---|
| Манифест | `v` (версия схемы) | до запуска |
| Манифест | `run_id`, `game`, `kind` (`probe`\|`shots`\|`play`\|`sim`\|`golden`\|`all`) | до запуска |
| Манифест | `git.rev`, `git.dirty` | до запуска |
| Манифест | `buildHash`, `configHash` (`forge.config` + `scenarios` + `adapter`) | до запуска |
| Манифест | `seed`, `botPolicy`, `nRuns` | до запуска |
| Манифест | `renderer`/`headless`, `chromiumVersion`, `machine`, `toolVersions` | до запуска |
| Манифест | `command` (точная команда запуска) | до запуска |
| Манифест | `actor.sessionId` — из `CLAUDE_CODE_SESSION_ID` | до запуска |
| Результат | `durationS`, `exitCode`, `verdict` | конец запуска |
| Результат | `scorecard` (≤12 чисел) | конец запуска |
| Результат | `artifactsDir` (пути к PNG/HTML/`runs.jsonl`) | конец запуска |

**Кто запускал — без дисциплины агента.** `forge` читает `process.env.CLAUDE_CODE_SESSION_ID` — эта переменная утекает в любой Bash-потомок Claude Code (измерено в спайке Пульта, `tools/pult/spike/env/capture-env.log.jsonl`). Для Codex и opencode такой переменной не установлено → `actor.kind = 'unknown'` либо ручной `FORGE_ACTOR`. Задача = сессия + git-ветка.

**Упавший, прерванный и зависший прогон тоже оставляет запись** — манифест уже на диске, результат дописывается со статусом `aborted`/`crashed` вместо `ok`/`needs-work` (находка Codex: без этого «упавший прогон» просто не существует для журнала).

**Committed vs ignored.** В git идёт только сам файл записи (`.forge/ledger/<дата>/<run_id>.json`, размер до ~1,5 КБ). Тяжёлые артефакты (PNG, `runs.jsonl`, HTML-отчёт) остаются вне git в `.forge/<kind>-<stamp>/`, как сегодня. `forge prune --keep 20` чистит только их и никогда не трогает прогоны, на которые ссылается `baseline.json` или `golden/`.

**`cmp_key`** = хэш от `(game, config_sha256, bots, renderer, n_runs, headless, machine)`. Прогоны с разным `cmp_key` не сравниваются без `--force`, и тогда каждая дельта помечена «НЕ СРАВНИМО» — это и есть защита от «сравнили 20-прогонный симулятор с 60-прогонным на другой машине и сделали вывод».

## 5. Что видит Павел

- **`forge log -n 20`** — таблица: `run_id`, дата, кто (claude/codex/opencode/человек), `kind`, вердикт, 4 главных числа, стрелка к предыдущему сравнимому прогону. Это и есть ответ на «видеть, как гоняешь» — после факта, в терминале и в PR-диффе.
- **`forge compare --last 2 | <A> <B> | --baseline`** — таблица дельт. Считается доверительный интервал **разности** двух прогонов (**доверительный интервал разности** — диапазон вероятных значений самой разницы между A и B; это не то же самое, что пересечение двух отдельных доверительных интервалов — на этой путанице Codex поймал оба дизайна, см. №4 в §13), а не пересечение интервалов Уилсона по отдельности. Если интервал накрывает ноль — пишем «неубедительно», не «шум»: ноль внутри интервала значит «недостаточно данных для вывода», а не «доказано, что разницы нет». При общих seed — парный анализ.
- Проверочный пример: находка Brick Breaker 14.09 (винрейт 0% → 100%, таймауты 20/20 → 0/20, медианный уровень 1 → 21) должна воспроизводиться одной командой `forge compare`.
- В существующем HTML-отчёте (`report.mjs`) — новая колонка «базовый прогон» и дельта. Новой страницы нет.
- Позже, в Forge Studio: одна панель «Прогоны» внутри уже утверждённой вкладки Tech — спарклайн по 30 последним прогонам, клик → отчёт. Только если `forge log` окажется мало.
- **Живого просмотра нет.** `forge watch` отвергнут всеми тремя критиками: приятно смотреть, но не меняет решений. «Что агент делает прямо сейчас» — работа Пульта (`pult agent tree`, `pult events tail`), расход и длительность — Пульт Ф2.

Мок формата (команды ещё не реализованы, числа — только там, где они реальны):

```
$ forge log -n 5 --game brick-breaker                                         # MOCK
run_id                                дата        кто     kind вердикт     winrate      ...
brick-breaker-<PLACEHOLDER>-a1b2c3    2026-09-14  claude  sim  needs-work  0% (0/20)    <PLACEHOLDER>
brick-breaker-<PLACEHOLDER>-d4e5f6    2026-09-14  claude  sim  ok          100% (20/20) <PLACEHOLDER>  ↑
```

```
$ forge compare brick-breaker-<PLACEHOLDER>-a1b2c3 brick-breaker-<PLACEHOLDER>-d4e5f6   # MOCK
metric        A (до фикса)  B (после фикса)  дельта         вердикт
winrate       0%            100%             +100 п.п.      достоверно (CI разности не пересекает 0)
таймауты      20/20         0/20             −20            достоверно
medianLevel   1             21               +20            достоверно
<...>         <PLACEHOLDER> <PLACEHOLDER>    <PLACEHOLDER>  <PLACEHOLDER>
```

Реальные числа в мок-таблице — из проверочного примера Brick Breaker 14.09 (SYNTHESIS-OBSERVABILITY.md, а не выдумка); всё остальное — заглушка формата.

## 6. Цифры игры

- `minN ≥ 30`: вместо процента печатается «мало прогонов» — иначе доля из 5 бот-заходов выглядит как факт.
- `brokenBotRate`: доля прогонов, где бот зациклился, не двигал ключ прогресса или упёрся в `maxTicks`; такие прогоны исключаются с явной строкой. Сегодняшний `bot-suspect` ловит только случай «ветеран хуже новичка».
- Урок bum2billionaire: выбор политики бота качнул результат сильнее, чем проверяемая механика.
- Любой вывод симуляции — наблюдение, не доказательство. «Проходимо ботом» ≠ «интересно человеку»: метрики удовольствия нет нигде, и этот дизайн её не даёт.

## 7. Цифры картинки — честно

Автоматической «оценки красоты» для стилизованной графики не существует: модели вроде BRISQUE/NIQE/CLIP-IQA обучены на фотографиях и примут плоскую заливку за дефект; VLM-судья с баллом 1–10 ненадёжен. Поэтому шесть слоёв, и поздний никогда не перекрывает ранний — от самого дешёвого и надёжного к самому дорогому и наименее надёжному:

| Слой | Что меряет | Гейт? | Когда врёт |
|---|---|---|---|
| 1. Живой ли кадр | `frame-alive` (есть) — различимость цветов, диапазон яркости | Гейт | Ловит только «ничего не отрисовалось»; полностью сломанный, но цветной кадр пройдёт |
| 2. Читаемость интерфейса | WCAG-контраст (**WCAG-контраст** — формула из веб-стандарта доступности: отношение яркости текста к фону, чем выше число, тем легче прочитать) + размер зон нажатия, по границам элементов из дампа сцены | Совещательное, не гейт сабмита | Не видит текст, запечённый в атлас; на текстурном/полупрозрачном фоне нужна выборка по области, а не одна точка |
| 3. Дрейф картинки | `pixel_drift_pct` через `odiff` против golden-эталона (**golden-эталон** — заранее одобренный «правильный» скриншот, с которым сравнивают новые кадры) | Сначала только логируется; гейтом — после ≥20 прогонов с измеренной долей ложных срабатываний | Любое легитимное изменение арта проваливает шот, пока эталон не обновлён; шрифты/GPU-драйвер/версия Chromium двигают пиксели без изменения кода |
| 4. Соответствие стилю | clip%, яркость p1/p50/p99, попадание в палитру, доля тёмных пикселей — `echo-art-critic`'овский inline-скрипт становится файлом в `game-forge` | Не гейт, не сравнивается между играми | Пороги ещё помечены `default` — ждут заморозки `STYLE_GUIDE.md` |
| 5. Мнение | Парное сравнение «текущий кадр против базового» VLM-судьёй, порядок сторон случайный, оба порядка усредняются | Аннотация, не число и не гейт | VLM ранжирует пары приемлемо, но не умеет надёжно ставить баллы (~5% остаточная позиционная погрешность); включается, только если на 10 парах с известным Павлу ответом совпало ≥7 |
| 6. Человек | 100%-кропы, два варианта, выбор Павла — без изменений | Финальное слово | Не врёт — но это ручной труд, автопроверка не считается за приёмку |

Вне скоупа: Elo-рейтинг картинок, NR-IQA (BRISQUE/NIQE/CLIP-IQA) как гейт, LPIPS (тянет PyTorch), FLIP — только если `odiff` окажется слишком строгим, Feature Congestion.

## 8. Цифры процесса

`forge process --since 14d` — офлайн, без хуков и сборщиков. Источники: записи прогонов + `git` + транскрипты Claude Code (`sessionId`, `timestamp`, `message.model`, `message.usage`, команды Bash в `tool_use.input.command`; субагенты — отдельными файлами `subagents/agent-<id>.jsonl`, связка по `toolUseId`).

Метрики: прогонов до зелёного, время до зелёного, проскочившие регрессии, живучесть кода через 7 дней (только как направление). Токены и стоимость — **не здесь**, это Пульт Ф2.

Предохранители от закона Гудхарта (**закон Гудхарта** — если метрика становится целью, её начинают «делать красивой» вместо того, чтобы улучшать то, что она должна отражать; здесь: агент, который реже гоняет `forge`, выглядит эффективнее, а не лучше):
- «прогонов до зелёного» никогда не печатается без «проскочивших регрессий» рядом;
- эпизод, в котором правили эталоны, сценарии или бюджеты, помечается `tainted` и выпадает из медиан;
- медианы только при ≥10 эпизодов, иначе «мало данных»;
- доказательства (`golden`, `invariants`, `budget`) проверяются прогоном, который чинивший агент не контролирует — отдельный каталог сам по себе границей доверия не является (находка Codex, №7 в §13).

Поправка к kill-критерию Г1: две недели разнородных задач не доказывают, что `replay` ускорил починку. Число — подсказка к решению, а не приговор `scene dump`'у. Критерий «Павел не пользовался» заменяется счётчиком вызовов `forge log`/`forge compare` — механика вместо самоотчёта.

## 9. Производительность

Все числа `probe` сняты в headless Chromium на Mac и подписываются «desktop-headless, на устройстве не проверено». Приёмка — на реальном Android; этот гейт в плане движка уже есть (§7 `docs/plans/2026-09-20-forge-engine-design.md`), у Эха Океана замер fps на Android уже ждёт Павла — тот же гейт, просто пришедший раньше этого документа.

## 10. Граница с Пультом

- Правило: нужно ли для числа собрать и запустить игру? Да → Forge. Нет → Пульт.
- Пульт: сессии, дерево агентов, разрешения, расход, ветки. Forge: что произошло внутри прогона игры.
- Единственный стык — строка: Forge пишет `actor.sessionId` (из `CLAUDE_CODE_SESSION_ID`) в запись прогона. Когда появится Пульт Ф3, его нода «Shell» (в доках прямо: «скрипт: тесты, `forge probe`, сборка») выставит свой id так же. Без протокола и IPC — просто чтение одного файла.
- Следствие: вкладка «Claude» и хук `forge_feed.py` из плана Forge Studio уходят в Пульт — это его мандат дословно.

## 11. Бюджет (рекомендация, ждёт решения Павла)

Новое: запись прогона 0,5д + `forge log`/`compare` 1,0д + `forge process` 1,0д + `minN`/`brokenBotRate` 0,75д + контраст/pixelstats 1,0д = **4,25 дня**. `pixel-diff` и `replay` уже в плане движка — не добавляются повторно.

Чем платим (это пункты утверждённого 18.09 плана Studio, поэтому решает Павел):
- лента агента / вкладка Claude → в Пульт: −0,5д;
- тап-хитмап и кнопка фидбэка в один тап → −1,0д (при 3–5 тестерах данных не наберётся, сообщение в Telegram дешевле);
- `forge fx` (обёртка Arcada Effector) → −1,0д сейчас, возвращается, когда автор даст лицензию — без неё вендорить нельзя.

Освобождается 2,5д → чистая прибавка **+1,75 дня**. Тюнер **не** трогаем (Павел просил, нужен балансу Самовара). Г1 остаётся ≤9 дней. Г2: +1,75д — решается в начале Г2, либо вместо дня `@forge/kit`, либо не строится.

## 12. Первый срез (Codex, <0,5 дня, сразу после Г0)

Один прогон «Самовара» оставляет версионированный манифест + ссылки на существующий HTML-отчёт и кадры, точную команду, exit-код, измеренные числа. Павел смотрит одну полную запись. Ноль новых команд, сборщиков и интерфейса. Всё остальное строится, только если эта запись пригодилась на неделе kill-теста.

| 3 (крупная) | Ненадёжная запись прогона: закоммиченный append-only `ledger.jsonl` конфликтует между ветками; `prune`/теги/обновление baseline мутят «неизменяемость» | Один JSON-файл на прогон вместо общей строки — новые файлы с уникальными именами не конфликтуют; `prune` не трогает файлы записей, только тяжёлые артефакты | §4 |

## 14. Слабые места (честно)

- Первые ~20 прогонов журнал — чистый оверхед: сравнивать не с чем.
- Это инструментирование, то есть ровно та форма, в которой однажды вышло 13 тыс. строк мета-систем и ноль билдов. Защита одна: первый срез 0,5 дня и правило «дальше — только если пригодилось».
- Для Codex и opencode авторство прогона пока неизвестно.
- Главное качество игр — интересно ли играть — остаётся неизмеренным.

## 15. Открытые вопросы

- Идентификатор сессии для дочерних процессов Codex/opencode — у Claude Code есть `CLAUDE_CODE_SESSION_ID`, у остальных CLI такой переменной нет; решение (ручной `FORGE_ACTOR`?) не выбрано.
- WCAG-контраст на текстурном или полупрозрачном фоне — однопиксельная выборка может «повезти» на удачном фоне; нужна ли выборка по области, и как её специфицировать, не решено.
- Достаточно ли стабилен формат транскриптов Claude Code для `forge process`, чтобы строить на нём парсер, который не будет ломаться при каждом обновлении инструмента.
